# Phase 3 plan: reliability, observability, cost

> **Status: done.** Every criterion below was checked on kind on 2026-10-28; results and evidence in [`docs/phase-3-results.md`](../phase-3-results.md).

Goal: the proof. FinCore is observable end to end (metrics, logs, traces, SLOs with burn-rate alerts), its limits are measured (load test), its failure modes are exercised (chaos, with postmortems), it can be restored into a new cluster with measured RTO/RPO, and its cost is known. The client-facing docs (ADRs, runbooks, demo script, portfolio, a README written as a case study) complete the project.

As in Phases 1 and 2, everything is proven on `kind`. AWS-only parts (AWS FIS, Aurora failover and snapshots, real cost, `up.sh`/`down.sh`) are written and statically checked, never run.

## Design notes

- **SLIs:**
  - availability = `POST /v1/payments` answered without a 5xx (declines are correct answers);
  - latency = share under 300 ms (the `le="0.3"` bucket).
  
  Alerts follow the multi-window, multi-burn-rate pattern from the Google SRE workbook (14.4× over 1 h and 5 m, 6× over 6 h and 30 m page; 3× and 1× ticket). Recording rules and alerts are tested with `promtool`.
- **Business dashboard.** Payments per second by outcome, capture rate, captured volume, outbox backlog, failing webhook deliveries (the ones that end in the DLQ; the DLQ's depth itself is an SQS CloudWatch metric on AWS), and the ledger's live imbalance (must be 0). Dashboards are generated by `dashboards/generate.py`; `make check` fails when the committed JSON is stale.
- **Tracing.** payments-api → ledger is already instrumented (otelhttp). Parent-based sampling at 10 %: a request that arrives with a sampled `traceparent` is always recorded, which is how the demo follows one payment. Loki derives `trace_id` from the JSON logs and links to Tempo; Tempo links back to the logs. Spans leave the CDE through one more explicit NetworkPolicy (egress to Tempo on 4318 only).
- **Logs.** Fluent Bit keeps the line as the service wrote it (JSON) and adds only low-cardinality labels (namespace, app, container, pod). On kind it tails only the FinCore, data, Vault, Kyverno and Argo Rollouts namespaces.
- **Load test.** Runs as an in-cluster k6 Job (a port-forward would be the bottleneck). It is allowed through the CDE NetworkPolicy by its own label and admitted by Kyverno as an approved, digest-pinned image.
- **Chaos on kind:** pod kills, a node drain, and zone loss by cordoning and draining. The single CDE node is itself a finding: on AWS the `cde` NodePool spans three AZs. DB failover is a PostgreSQL restart; on AWS `scripts/chaos-aws.sh` uses AWS FIS and `aws rds failover-db-cluster`.
- **DR:**
  - Velero backs up the cluster state that is not in git (secrets, including the KMS seed on kind);
  - PostgreSQL is dumped consistently (`pg_dump`, a CronJob to S3);
  - Vault is backed up with Raft snapshots through a dedicated Kubernetes-auth role (snapshot only).
  
  `kind-up.sh --restore` recreates the cluster, restores secrets and data before the services start, and GitOps recreates everything else. RTO is measured to the first successful payment, RPO as the age of the newest backup at the time of the disaster.
- **Cost.** AWS prices are taken from AWS's public price list for ap-southeast-1, with the source and date recorded and nothing guessed. Cost per 1,000 payments uses the measured sustained throughput.

## Risks

| Risk | Mitigation |
|---|---|
| Memory: about 2.5 GB is free on the 10 GB VM (the maximum allowed without the owner) | Monolithic Loki and Tempo with small limits; Fluent Bit instead of Alloy; no OTel collector; short retention; Velero node agent not needed (consistent app-level backups instead of volume copies) |
| kind cannot sustain 300 RPS | Publish the measured maximum and why. The thresholds stay unchanged. |
| A restore depends on ordering (KMS seed before Vault, dumps before the services) | Explicit restore stage in `kind-up.sh` before Argo CD syncs the services; drill asserts the ledger invariant |

## As built: deviations and what the work found

| Plan | As built | Why |
|---|---|---|
| Alertmanager's kind receiver is the demo webhook sink | Named `page` and `ticket` receivers with no integration in git; the chaos evidence reads each alert's receiver from Alertmanager's API | The sink accepts only HMAC-signed FinCore webhooks |
| Burn-rate alerts cover availability | Plus `PaymentsAPIUnavailable` / `LedgerUnavailable` (no instance reachable for 1 minute) | In a total outage (zone loss), the servers report nothing, so a server-side burn rate has nothing to count |
| Load test ramps to 300 payments/s | Steps 20–150/s, each judged against the SLOs; the highest step within them is published | The laptop-sized kind cluster serves the offered rate up to ~90/s, but its p99 stays ≤ 300 ms only at lower rates (single PostgreSQL stand-in's commit latency), and beyond ~110/s it falls over. Longer overloads destabilise the VM for the experiments that follow. |
| Zone loss = cordon and drain one zone | Two experiments: `node-drain` (graceful, PDBs respected) and `zone-loss` (zone c frozen abruptly with `docker pause`) | One node per zone on kind makes "drain the zone" and "drain a node" the same thing; an abrupt loss is the harder, more realistic case |
| Velero restores the cluster state | Velero restores the secrets git does not hold; Vault (Raft snapshot) and PostgreSQL (`pg_dumpall`) have their own consistent backups; `kind-up.sh --restore` orders them (restore hold in the app-of-apps) | Volume copies of running databases are not consistent; app-level backups are |
| OpenCost with custom pricing on kind | Every kind node priced as an AWS m7g.large from the public price list, split per vCPU and GiB in OpenCost's own default ratio | kind has no price list; m7g.large is the system node type |

Problems the Phase 3 tests found in earlier phases' code, all fixed with tests and released through canaries (details in `docs/decisions-log.md` and the two postmortems):

1. The ledger's imbalance gauge scanned the whole ledger on every replica every 15 s, and became the database's largest load. Now one fleet-wide check per minute.
2. Readiness pinged the database through the request pool, so pods flapped NotReady under load. Now it gates on dependencies only until they are first reached.
3. Connection pools × autoscaling exceeded the database stand-in's memory. There is now a connection budget of 5 per pod and 100 at maximum replicas.
4. No connect timeout: a 6 s database restart caused 2 minutes of failures. Now `DB_CONNECT_TIMEOUT` is 5 s.
5. kube-prometheus-stack's runtime-patched webhook CA kept Argo CD in a sync loop. The CA bundle is now ignored.
6. AWS (static): Vault's three replicas could never all schedule on a 2-node system group. The group now has 3 nodes.
7. `deploy-kind.sh` could start a second canary before Argo CD applied the first; it now waits for Argo CD to apply the tag.
8. The Vault injector never failed closed (Phase 2 values used the deprecated `injector.failurePolicy`). It now does, and `make check` asserts it.
9. Argo CD sync waves could run ahead: a child Application looked Healthy before its first sync. Its health check now waits for that sync.
10. Restore-specific (DR drill trials): backups named after their start time, Velero's schedule paused and Vault restored into one node (restarted after the snapshot) during a restore, the snapshot copy checksum-verified, the Argo CD chart installed from the pinned cache, client-side apply for Argo CD upgrades, and longer repo-server probes on kind.
